# Технические решения

## 2026-10-22 — Детализированные мышцы и страницы упражнений

**Решение:** добавляем `muscles` и связь `exercise_muscles` с ролью `primary`/`secondary`, а также английскую инструкцию в `exercises`. Утверждённые 70 упражнений и их метаданные заполняются идемпотентным seed-скриптом; старые записи обновляются по имени без смены `id`. Персональная история запрашивается отдельным защищённым API. Схема тела хранится локально как SVG и не передаёт данные внешним сервисам.

**Причина:** отдельная таблица мышц поддерживает детализацию и повторное использование между упражнениями, а отдельная связь фиксирует роль без дублирования. Стабильность `id` сохраняет существующие тренировки и рутины.

## 2026-10-22 — История веса и периоды графиков

**Решение:** новая таблица `body_weight_entries` хранит пользователя, вес и время записи. Новая точка создаётся при изменении `body_weight_kg` через профиль; очистка поля и сохранение прежнего значения историю не переписывают. Миграция создаёт по одной точке для существующих ненулевых весов с временем миграции. Графики фильтруют записи по местному календарю устройства: текущая неделя, месяц или последние 3/6/12 календарных месяцев.

**Причина:** одно текущее значение профиля не позволяет построить историю; дата прошлого измерения неизвестна и не должна выдумываться. Записи принадлежат пользователю, а периоды не влияют на сохранённые данные.

## 2026-10-22 — Аналитика и длительность тренировки

**Решение:** `GET /workouts/progress` отдаёт только выполненные подходы завершённых тренировок текущего пользователя. Интерфейс вычисляет календарные неделю и месяц в часовом поясе устройства, объём, максимум веса/повторений и точки графика. `PATCH /workouts/{id}/time` теперь принимает `started_at` и `duration_minutes` вместо двух времён; сервер сам вычисляет `finished_at` и проверяет, что оно не в будущем. Схема БД не меняется.

**Причина:** все показатели выводятся из уже сохранённых данных, без дублирующих таблиц. Местный календарь соответствует тому, как пользователь видит даты. Длительность исключает ошибку ручного выбора даты окончания при переходе через полночь.

Здесь фиксируются решения, которые влияют на архитектуру проекта, модель данных или API, и кратко объясняются их причины.

## 2026-10-21 — Запланированные подходы и отмена тренировки

**Решение:** `RoutineSet` хранит запланированные вес, повторения и позицию подхода внутри упражнения рутины. API рутин сохраняет обратную совместимость с `exercise_ids` и добавляет необязательный `planned_sets`: упорядоченный список записей с `exercise_id`, `weight_kg` и `repetitions`. При запуске рутины упражнения и подходы копируются в новую тренировку одной транзакцией; все подходы невыполненные. `DELETE /workouts/{id}` доступен только владельцу активной тренировки и атомарно удаляет подходы, упражнения и саму тренировку. Завершённая тренировка отвечает `409`.

**Причина:** существующие рутины без подходов остаются рабочими, а копирование отделяет план от фактического результата. Отмена полностью убирает ошибочно начатую активную тренировку без появления записи в истории. Подтверждение в интерфейсе предупреждает о необратимой потере данных.

## 2026-10-21 — Рутины и история последнего подхода

**Решение:** первоначально рутина принадлежала пользователю и содержала только название и упорядоченные уникальные ссылки на упражнения каталога. `POST /routines`, `GET /routines`, `PUT /routines/{id}` и `DELETE /routines/{id}` управляют ими; `POST /routines/{id}/start` создаёт тренировку. При наличии активной тренировки возвращается `409`. `GET /exercises/{id}/last-set` возвращает только последний по `sets.id` подход текущего пользователя либо `404`, если истории нет. Подстановка происходит только в форме и не сохраняется без действия пользователя. Решение о содержимом рутины расширено выше в рамках следующего этапа.

**Причина:** рутина описывает план упражнений, а не повторяет прошлый результат. Отдельная подсказка по истории не перезаписывает прошлые тренировки и не связывает будущую тренировку с изменяемым шаблоном. Порядок по идентификатору подхода сохраняет предсказуемость при ручной корректировке дат тренировок.

## 2026-09-24 — Первый стек проекта

**Решение:** Python + FastAPI + PostgreSQL для backend; React + TypeScript для frontend.

**Причина:** стек соответствует текущим навыкам автора и востребован для backend/full-stack стажировок. React и TypeScript развивают нужный для рынка фронтенд-минимум.

## 2026-09-24 — Мышцы упражнений не входят в MVP

**Решение:** поля `primary_muscles` и `secondary_muscles` пока не добавляются.

**Причина:** каталог упражнений остаётся отдельной сущностью, поэтому позже можно добавить таблицы `muscles` и `exercise_muscles` с ролью `primary` или `secondary` через миграцию БД, не ломая тренировочные данные.

## 2026-09-26 — Базовые инструменты разработки

**Решение:** backend строим на FastAPI, SQLAlchemy и Alembic; frontend — на React, TypeScript и Vite. PostgreSQL можно запускать локально или через Docker Compose.

**Причина:** FastAPI даёт понятный HTTP API и автоматическую документацию, SQLAlchemy отделяет Python-модели от SQL, а Alembic ведёт историю изменений схемы БД. Vite быстро создаёт среду React-разработки. Docker Compose остаётся воспроизводимым вариантом запуска, а локальная PostgreSQL удобна для текущей учебной разработки.

## 2026-09-30 — Профиль при регистрации

**Решение:** при регистрации обязательны только никнейм и пароль. Поля `height_cm` и `body_weight_kg` могут быть `NULL` и заполняются позднее в профиле.

**Причина:** это соответствует пользовательскому сценарию MVP и позволяет разделить создание аккаунта и заполнение данных профиля.

## 2026-10-03 — Валидация регистрации

**Решение:** никнейм должен содержать от 3 до 50 символов, пароль — от 8 до 128 символов. Email не входит в MVP.

**Причина:** ограничения совпадают с моделью данных и позволяют API отклонить некорректный запрос до обращения к PostgreSQL. Email не требуется основному сценарию регистрации по никнейму и паролю.

## 2026-10-05 — Строка подключения к базе данных

**Решение:** `DATABASE_URL` передаётся через переменную окружения, а не хранится в репозитории.

**Причина:** URL содержит пароль PostgreSQL. Такой подход не допускает попадания секрета в Git и одинаково подходит приложению и Alembic.

## 2026-10-05 — Регистрация пользователя

**Решение:** регистрация выполняется запросом `POST /auth/register`. При успехе API возвращает HTTP `201` и публичные данные пользователя без пароля и `password_hash`; при занятом никнейме — HTTP `409`. Регистрация не выполняет вход автоматически. Пароль хешируется Argon2 через `pwdlib` с рекомендуемыми настройками.

**Причина:** отдельные регистрация и вход соответствуют сценарию MVP и упрощают первый API-контракт. Ответ не должен раскрывать пароль или его хеш. Argon2 — рекомендуемый FastAPI алгоритм для хеширования новых паролей.

## 2026-10-11 — Вход и access token

**Решение:** вход выполняется запросом `POST /auth/login` с никнеймом и паролем. При успехе API возвращает JWT `access_token` типа `bearer`, подписанный алгоритмом HS256 и действующий 30 минут. Секрет подписи берётся только из `JWT_SECRET_KEY`. Неверный никнейм и неверный пароль оба возвращают HTTP `401` с одинаковым сообщением `Invalid nickname or password`.

**Причина:** JWT позволит на следующем шаге идентифицировать пользователя на защищённых маршрутах без хранения серверной сессии. Одинаковая ошибка не раскрывает, зарегистрирован ли конкретный никнейм. Время жизни ограничивает последствия возможной утечки токена; секрет не попадает в Git.

## 2026-10-11 — Защищённый профиль текущего пользователя

**Решение:** `GET /auth/me` требует заголовок `Authorization: Bearer <access_token>`. Зависимость `get_current_user` проверяет подпись и срок действия JWT, получает id пользователя из `sub` и загружает пользователя из БД. При отсутствии, повреждении или истечении токена, а также при отсутствии пользователя API возвращает HTTP `401`.

**Причина:** endpoint не принимает id в URL, поэтому пользователь может получить только собственный профиль. Единая зависимость будет использоваться повторно в следующих защищённых маршрутах.

## 2026-10-11 — Частичное изменение профиля

**Решение:** `PATCH /auth/me` обновляет только переданные поля `height_cm` и `body_weight_kg`; оба значения должны быть положительными. Вес ограничен значением `999.99` и двумя знаками после запятой, чтобы соответствовать `Numeric(5, 2)` в PostgreSQL. Явное `null` очищает поле, а поле, отсутствующее в JSON, остаётся без изменений. Пустой JSON-запрос отклоняется с HTTP `422`.

**Причина:** PATCH предназначен для частичных изменений. Различение отсутствующего поля и `null` даёт пользователю возможность как заполнить, так и очистить данные профиля без случайной потери второго значения.

## 2026-10-14 — Хранение access token во frontend

**Решение:** frontend MVP сохраняет JWT access token в `localStorage`, после чего загружает профиль через `GET /auth/me`. При ошибке авторизации токен удаляется, а пользователь возвращается к форме входа.

**Причина:** это простой и наглядный способ сохранить сессию после перезагрузки страницы во время учебной локальной разработки. Для production-приложения стоит отдельно рассмотреть более защищённый вариант с HTTP-only cookie и защитой от XSS.

## 2026-10-15 — Категории и упражнения с собственным весом

**Решение:** начальный каталог использует категории `chest`, `back`, `arms`, `legs`, `shoulders` и `core`. Отжимания, отжимания на брусьях, подтягивания, выпады, планка и скручивания имеют `is_bodyweight=True`.

**Причина:** категории дают простую группировку MVP-каталога. Флаг `is_bodyweight` позволит будущему интерфейсу подходов не требовать рабочий вес для упражнений с собственным весом. Детализация основных и вторичных мышц останется отдельным будущим расширением через таблицы связей.

## 2026-10-15 — Чтение каталога упражнений

**Решение:** `GET /exercises` возвращает общий каталог упражнений без JWT и сортирует его по `category`, затем по `name`. Начальные данные добавляются идемпотентным скриптом `python -m app.scripts.seed_exercises`.

**Причина:** каталог не содержит персональных данных и понадобится до создания тренировки. Стабильная сортировка делает ответ предсказуемым для frontend, а повторный запуск seed-скрипта не создаёт дубликатов.

## 2026-10-15 — Активная тренировка и история

**Решение:** тренировка создаётся для текущего пользователя и имеет статус `active`. У пользователя может быть только одна активная тренировка. После завершения её статус меняется на `completed`, а запись появляется в истории этого пользователя; активная тренировка отображается отдельно от истории.

**Причина:** связь с пользователем не позволит увидеть или изменить чужие тренировки. Отдельная активная тренировка устраняет неоднозначность с таймером, а история остаётся списком законченных тренировок с датой и длительностью.

## 2026-10-15 — Получение текущей тренировки

**Решение:** защищённый маршрут `GET /workouts/active` возвращает активную тренировку текущего пользователя с HTTP `200`. Если её нет, API возвращает HTTP `404` с сообщением `No active workout`.

**Причина:** frontend сможет восстановить тренировку и её таймер после обновления страницы. Отсутствие активной тренировки — ожидаемое состояние, которое интерфейс обработает показом кнопки начала тренировки.

## 2026-10-15 — Уникальность упражнения в тренировке

**Решение:** упражнение из каталога можно добавить в конкретную тренировку только один раз. Повторная работа с ним фиксируется дополнительными подходами, а не второй записью упражнения.

**Причина:** это упрощает отображение тренировки и предотвращает дублирование одной сущности упражнения. Ограничение будет закреплено уникальной парой `workout_id` и `exercise_id` на уровне базы данных.

## 2026-10-15 — Добавление упражнения в активную тренировку

**Решение:** `POST /workouts/{workout_id}/exercises` принимает только `exercise_id`. Маршрут доступен только владельцу активной тренировки; сервер назначает следующую `position`. Несуществующая, завершённая или чужая тренировка, а также отсутствующее упражнение возвращают HTTP `404`; повторное упражнение в той же тренировке — HTTP `409`.

**Причина:** клиент не может подделать владельца, статус или порядок. HTTP `404` не раскрывает другому пользователю существование чужой тренировки, а HTTP `409` ясно сообщает о нарушении правила уникальности упражнения.

## 2026-10-20 — Чтение упражнений тренировки

**Решение:** защищённый маршрут `GET /workouts/{workout_id}/exercises` возвращает упражнения принадлежащей текущему пользователю тренировки в порядке `position`. Маршрут доступен как для активных, так и для завершённых тренировок.

**Причина:** frontend восстанавливает состав текущей тренировки после обновления страницы, а тот же контракт позднее можно использовать для просмотра истории без отдельного дублирующего endpoint.

## 2026-10-20 — Подходы упражнения

**Решение:** подход хранит положительное количество повторений, необязательный положительный вес до `999.99`, статус выполнения и серверную позицию. Для обычного упражнения вес обязателен, для упражнения с собственным весом может быть `NULL`. Новый подход создаётся невыполненным. Читать подходы можно и у завершённой тренировки, а создавать, изменять и удалять — только у активной тренировки владельца.

**Причина:** правила соответствуют сценарию MVP и типу `Numeric(5, 2)`. Разделение чтения и изменения позволяет позднее показать историю, не разрешая случайно менять завершённую тренировку через интерфейс активной тренировки.

## 2026-10-20 — Удаление упражнения из тренировки

**Решение:** `DELETE /workouts/{workout_id}/exercises/{workout_exercise_id}` доступен только владельцу активной тренировки и удаляет упражнение вместе со всеми его подходами. Frontend запрашивает подтверждение перед удалением.

**Причина:** подход не имеет смысла без упражнения, поэтому зависимые записи удаляются вместе. Ограничение активной тренировкой защищает завершённую историю от случайного изменения.

## 2026-10-20 — Завершение и история тренировок

**Решение:** `POST /workouts/{workout_id}/complete` меняет статус принадлежащей пользователю активной тренировки на `completed` и устанавливает серверное время `finished_at`. Невыполненные подходы не блокируют завершение и сохраняют свой статус. Повторное завершение возвращает HTTP `409`. `GET /workouts/history` возвращает только завершённые тренировки текущего пользователя, начиная с наиболее свежих.

**Причина:** серверное время даёт единый источник длительности, а сохранение статуса каждого подхода отражает фактически выполненную часть тренировки. После завершения пользователь может начать новую тренировку, а предыдущая остаётся доступной в истории.

## 2026-10-20 — Детальный просмотр истории

**Решение:** запись истории открывается в режиме чтения и загружает упражнения и подходы через те же защищённые endpoints, которые используются для восстановления тренировки. В деталях показываются вес, повторения и фактический статус каждого подхода.

**Причина:** единые endpoints исключают дублирование API и гарантируют одинаковое представление сохранённых данных. Отдельный режим чтения готовит интерфейс к следующему шагу — явному редактированию завершённой тренировки.

## 2026-10-20 — Редактирование завершённой тренировки

**Решение:** владелец может добавлять и удалять упражнения, а также создавать, изменять и удалять подходы как в активной, так и в завершённой тренировке. Редактирование завершённой тренировки не меняет её `started_at`, `finished_at` и статус `completed`.

**Причина:** это выполняет требование MVP о редактировании сохранённой тренировки и сохраняет первоначальную дату и длительность тренировки. Проверка владельца остаётся обязательной для всех операций.

## 2026-10-20 — Конфигурация окружения

**Решение:** backend получает `DATABASE_URL`, `JWT_SECRET_KEY` и `CORS_ORIGINS` через единый модуль конфигурации. Frontend получает адрес API из `VITE_API_URL`. Репозиторий содержит только безопасный шаблон `.env.example`, а настоящий `.env` игнорируется Git.

**Причина:** одна система имён устраняет расхождения между локальным запуском и Docker Compose. Секреты не попадают в Git, адреса можно менять без редактирования исходного кода, а обязательные значения проверяются при запуске.

## 2026-10-20 — Ручное изменение времени тренировки

**Решение:** владелец может изменить `started_at` и `finished_at` завершённой тренировки через `PATCH /workouts/{workout_id}/time`. Оба значения передаются вместе и должны содержать часовой пояс. Начало должно быть раньше окончания, а окончание не может находиться в будущем. Статус тренировки и её содержимое при этом не меняются.

**Причина:** пользователь может поздно включить таймер или занести тренировку после её окончания. Совместное обновление двух времён не оставляет запись в промежуточном некорректном состоянии, а серверная проверка сохраняет осмысленную длительность.

## 2026-10-20 — Адаптивный интерфейс Liftoff

**Решение:** оформляем существующий MVP в графитовой теме с мягким тёмно-зелёным акцентом. Разделяем интерфейс на главную, тренировку, историю, каталог и профиль; вход и регистрация находятся вне основной оболочки. Навигация использует hash-адреса (`#/workout`, `#/history/123`): кнопки браузера и обновление страницы работают без дополнительных правил маршрутизации сервера. На компьютере используется боковая панель, на телефоне — нижняя навигация и аватар для доступа к профилю.

**Причина:** это утверждённый пользователем визуальный стиль и структура существующих функций, без изменения API и модели данных. Общие UI-компоненты и единый редактор тренировки уменьшают дублирование кода и позволяют разбирать React по небольшим частям. Графика выполнена CSS и SVG, внешние шрифты и изображения для запуска не нужны.

## 2026-10-20 — Свайп вместо нумерации и постоянных кнопок удаления

**Решение:** порядковые номера упражнений и подходов не показываем; серверные `position` продолжают определять порядок. Свайп влево раскрывает удаление конкретного подхода или упражнения. Кнопка «…» открывает то же действие с мыши/клавиатуры и переводит фокус на него. Вложенный свайп подхода не активирует свайп упражнения; вертикальное движение остаётся прокруткой. Перед удалением показываем модальный диалог с отменой.

**Причина:** интерфейс не перегружен вторичными кнопками, но удаление остаётся доступным без жестов и защищено от случайного действия. ID и порядок в базе не меняются из-за визуального решения.

## 2026-10-20 — Состояния интерфейса и браузерные проверки

**Решение:** предусматриваем загрузку, пустые списки, повтор после сетевой ошибки, уведомления об успешном сохранении и централизованную обработку HTTP `401` для защищённых запросов. Неудачный вход и сетевой сбой не считаются истечением существующей сессии. Добавляем Playwright-тесты с отдельным тестовым Vite-сервером и подменённым API для desktop и mobile.

**Причина:** тесты проходят полный пользовательский путь через настоящий React-интерфейс, не создавая записи в пользовательской базе. Проверяются регистрация/вход, поиск, профиль, упражнения/подходы, свайп и подтверждение, история/время, повтор загрузки и выход при истечении токена. Backend остаётся покрыт отдельными интеграционными тестами.
